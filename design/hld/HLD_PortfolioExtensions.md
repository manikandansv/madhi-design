# HLD — Portfolio Extensions

## What this document covers

Design notes for two cross-phase evaluation and generation capabilities that are not core product features but augment the quality and regulatory accuracy of the AI outputs. These are portfolio-extension capabilities: they do not change what the user sees in the main flow, but they raise the reliability bar for what the AI produces.

Neither capability is implemented in Phases 1–4. Both are labeled here so the reasoning is documented and implementation can be planned independently.

---

## Extension 1 — LLM-as-Judge for Narration Evaluation

**Applicable from:** Phase 2 onward (once narration is generated in MilestoneSuggester)

**Category:** Evaluation tool, not a product feature. This is internal scaffolding — the user never interacts with the judge directly.

---

### Problem

The narration attached to each milestone (e.g., "Based on your ₹45,000 monthly income and two school-age children, a ₹25 lakh education corpus in 8 years requires roughly ₹18,000/month at 8% return") cannot be validated by exact string match or deterministic assertion. The numbers in the narration come from deterministic calculation; the prose around those numbers involves judgment about clarity, tone, and whether the explanation reflects the actual constraint.

Standard test harnesses can verify:
- That a milestone was returned (structure check)
- That the amount and timeline fields are numerically correct (deterministic output check)

Standard test harnesses cannot verify:
- Whether the narration accurately reflects the profile constraints used to generate it
- Whether the tone is appropriate for the user (plain-language vs. jargon)
- Whether the explanation is internally consistent (e.g., does the monthly SIP figure in the narration match the milestone's `monthlySip` field)

Without an evaluation mechanism for narration, regressions in prompt quality are invisible — a prompt change can silently degrade the quality of explanations while keeping numbers correct.

---

### Deterministic / AI split

**Deterministic (always):**
- The numbers the narration references: milestone amount, timeline, monthly SIP, rate-of-return assumption. These are computed arithmetically before the prompt is constructed and are asserted separately.
- Structural checks: narration field is non-empty, length is within bounds, no placeholder text left in output.

**AI (LLM-as-judge):**
- A separate model call receives the milestone's structured fields (amount, timeline, profile snapshot) and the generated narration.
- The judge scores the narration against a rubric with three dimensions:
  1. **Accuracy** — does the narration correctly reflect the numbers and profile constraints (e.g., child count, income, existing insurance)? Score 0–2.
  2. **Clarity** — is the explanation understandable to a non-finance user? No unexplained acronyms, no raw formula notation. Score 0–2.
  3. **Tone** — is the language matter-of-fact and supportive, not alarming or condescending? Score 0–1.
- The judge returns a structured score object, not free text. Total score out of 5.
- A threshold (e.g., ≥ 4) passes; below threshold is flagged for review.

**Model for judge:** A smaller, faster model than the generation model is appropriate — the judge does not generate prose, only scores it. Claude Haiku or equivalent.

---

### What breaks if this extension is removed

The narration generation still works. Milestone amounts and SIP figures remain numerically correct. The loss is observability: prompt regressions that degrade prose quality are invisible until a user complaint or manual review catches them. At prototype scale this is acceptable. At production scale, where prompt changes happen regularly, the judge provides the only automated signal that narration quality has regressed.

---

### Integration point

The judge runs as a post-generation step in the evaluation harness (CI or periodic batch), not in the live request path. A user request to `/api/milestones` does not invoke the judge. The judge is invoked:
- In CI against a fixed set of test profiles and expected-score thresholds
- Optionally in a nightly batch against a random sample of recently generated milestones

Output: a score per milestone narration, logged to a monitoring store. No user-facing surface.

## Extension 2 — RAG-Grounded Regulatory Explanation

**Applicable from:** Phase 3 onward (once tax and regulatory narration is generated)

**Category:** Generation quality improvement. The user sees the output (tax-rule narration), but the retrieval mechanism is internal.

---

### Problem

Phase 3 generates narration explaining Indian tax rules as they apply to a user's situation — for example, the Section 80C deduction limit, the new-regime vs. old-regime choice, the LTCG threshold on equity funds. This narration is generated by a language model.

Language model training data has a knowledge cutoff. Indian income tax rules change annually with the Union Budget. A model trained before a particular Finance Act will generate narration based on the previous year's rules. The error is silent: the narration reads fluently and confidently, but the limit or rate it states may be a year out of date.

This is not a hallucination — it is a staleness problem. The model is accurately recalling what it learned, but what it learned is no longer current.

---

### Deterministic / AI split

**Deterministic (always):**
- Tax arithmetic: the actual computation of tax liability, deduction amounts, effective rate, and savings differential. These are computed from the regulatory figures using code, not model generation. The model does not perform arithmetic.
- The regulatory figures themselves (e.g., Section 80C limit = ₹1.5 lakh, LTCG threshold = ₹1.25 lakh for FY 2024-25) are stored in a maintained, versioned corpus — not retrieved from model memory.

**AI (RAG-grounded generation):**
- At prompt time, the relevant regulation text is retrieved from the corpus based on the user's situation (deduction types applicable, regime choice, asset classes held).
- The retrieved text is injected into the prompt as context.
- The model generates the narration from the retrieved text, not from training memory.
- The narration explains the rule in plain language and connects it to the user's numbers (which come from deterministic calculation).

**Corpus:** A small, hand-maintained set of Indian tax regulation excerpts. Not a general legal database. Scoped to the rules that Phase 3 narrates: income tax slabs, standard deduction, 80C/80D/80CCD deductions, LTCG/STCG rules for equity and debt funds, NPS tax treatment. Updated once after each Union Budget.

---

### What breaks if this extension is removed

Narration still works. The model generates explanations from its training data. At the time of initial Phase 3 development, training data and current rules may be aligned. The failure mode is deferred: after the next Union Budget amendment, narration continues to generate without error, but may state a threshold or rate that has changed. The user receives plausible-sounding but outdated tax guidance. Because the narration reads fluently, the staleness is not visible without comparison to authoritative sources.

With RAG grounding: the corpus is updated post-budget, and all subsequent narration reflects the new rules immediately, without a model retrain or prompt change.

---

### Integration point

- **Corpus store:** A small document collection (JSON or Markdown files, version-controlled). Each document covers one regulation area with an effective-date field.
- **Retrieval:** Keyword or embedding-based lookup at prompt construction time. The query is derived from the user's tax profile (deduction types, regime, asset classes). Retrieval happens in the request path, before the model call.
- **Prompt construction:** Retrieved excerpts are prepended to the system prompt as `[REGULATION CONTEXT]`. The model is instructed to base its narration on the provided context and not on general knowledge where they conflict.
- **Fallback:** If retrieval returns no results (e.g., an edge case not covered in the corpus), the model falls back to training knowledge with a flag logged. No user-facing error.

---

## What these extensions do not do

- They do not change the user-facing product flow in Phases 1–4.
- The LLM-as-judge extension does not run in the live request path — it is evaluation infrastructure only.
- The RAG extension does not replace deterministic tax calculation — arithmetic is never delegated to retrieval or generation.
- Neither extension changes the milestone schema or the approval flow.
- Neither is a prerequisite for Phase 1–4 implementation — they extend quality, not correctness of core features.
